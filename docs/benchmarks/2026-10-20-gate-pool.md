# 2026-10-20 — Injection Gate reranker pool (30 vs 10)

**Commit:** the commit that introduces `GATE_POOL = 10` (parent `a0de1e3`)
**Bench:** `npm run eval:suite -- --tier fast` (coding-life, PrecisionMemBench, LongMemEval `_s` stratify 4), dev split, gate on
**N:** coding-life search 12 / session-start 2 / prompt-submit 9; pmb 47; LongMemEval 24
**Hardware:** linux x86_64, shared host at load average 25-40 (13 agents), Node 22+
**Embeddings:** on-device (suite default)
**LLM:** none
**Reranker:** the homelab `qwen3-rr-0.6b-q8` GGUF behind `AGENTMEMORY_PROMPT_RERANK_URL` (default host; the endpoint is not recorded here), `_MIN` 0.03, timeout 1000 ms

## Headline

Capping the reranker pool at the 10 best BM25 candidates changes no fast-tier metric (all 15 `≈`, Δ 0.000) and cuts the reranker call from p50 1855 ms to 656 ms. At 30 documents the call exceeds the gate's 1000 ms cap, so the full pool would time out and fall back to BM25 on every prompt. Shipped.

## Arms

| Arm | Pool | search R / P / hit | session-start R / P | prompt-submit R / P / hit | pmb pass | LongMemEval R@5 / hit |
|---|---|---|---|---|---|---|
| gate-pool-30 | 30 (previous) | 1.000 / 0.708 / 0.833 | 0.625 / 1.000 | 0.861 / 1.000 / 1.000 | 0.447 | 0.896 / 0.958 |
| gate-pool-10 | 10 | 1.000 / 0.708 / 0.833 | 0.625 / 1.000 | 0.861 / 1.000 / 1.000 | 0.447 | 0.896 / 0.958 |

`--against gate-pool-30` reports every metric `≈` with a [0.000, 0.000] interval. The baseline floors in `eval/baselines/coding-agent-life-v2.json` are for the BM25 adapter; the gated `agentmemory` adapter's prompt-submit recall (0.861) is under that floor's 0.907 in both arms, so the change neither crosses nor widens it.

## Latency

Controlled probe (`tmp/probe/pool.mjs`, not committed): 25 interleaved POSTs per size to the reranker with 400-char documents and an 80-char query, same documents, first N of 30.

| Pool | p50 | p95 | min | max |
|---|---|---|---|---|
| 30 | 1855 ms | 2077 ms | 1640 ms | 2521 ms |
| 10 | 656 ms | 742 ms | 557 ms | 1117 ms |

Latency is near-linear in documents (~60 ms each, contended host). The suite's own prompt-submit p50/p95 (pool 30: 51/117 ms; pool 10: 83/192 ms) are not comparable: the gate-free `search` path also rose (15 to 84 ms) because the host load differed between runs. Neither arm timed out in the suite; the eval corpus is small, so few candidates pass the BM25 floor and the pool rarely reaches 10, which is why quality is identical. The suite tears its sandbox down, so `/diagnostics` `injection-gate` counts were not captured; the probe replaces them. `eval:replay` was not run.

## Methodology

Both arms ran the same build apart from `GATE_POOL`. The pool is the first N candidates after the BM25 floor, seen-ref filter and session-summary filter. A failed gate (timeout, malformed) still falls back to all candidates, so BM25 behaviour is unchanged.

## Calibration observations (model not changed)

- The reranker's scores saturate: on 30 related documents 28 scored 0.98-0.998 and the lowest 0.906. `AGENTMEMORY_PROMPT_RERANK_MIN` 0.03 therefore cuts only clearly unrelated candidates; ordering among related ones is carried by the third decimal.
- A document's score is the same at pool 10 and 30 (0.998 in both for the first three), so shrinking the pool does not shift scores, only the candidates considered.
- A reranker with spread scores would let `_MIN` act as a relevance bar; that needs a model swap, which is outside this repo.

## Reproduce

```sh
git checkout <sha> && npm ci && npm run build
export LONGMEMEVAL_PATH=~/datasets/longmemeval/longmemeval_s.json AGENTMEMORY_PROMPT_RERANK=on AGENTMEMORY_PROMPT_RERANK_URL=<reranker>
npm run eval:suite -- --tier fast --label gate-pool-10 --against gate-pool-30   # pool 30: set GATE_POOL = 30
```

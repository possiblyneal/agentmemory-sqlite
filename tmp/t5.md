## What to build

The daemon's Health Verdict stops flipping on a single reading. A Verdict changes only after three consecutive samples agree on the new one, in both directions — so roughly ninety seconds of sustained trouble before `critical` is published, and the same again before recovery is declared.

This matters because an external supervisor reads the published Verdict as a restart signal. Today one slow garbage collection inside a thirty-second sampling window is enough to trigger it.

Verdict evaluation stays a pure function. Rather than layering hysteresis on top of it, fold it in: the function takes the current sample together with the previously published Verdict and the run of consecutive samples disagreeing with it, and returns the Verdict to publish plus the updated run. The monitor holds that state in its own closure and deliberately does not persist it — a restart legitimately resets the judgement.

The counts are fixed at three in this ticket; making them configurable is a later ticket.

## Acceptance criteria

- [ ] A single sample disagreeing with the published Verdict does not change it.
- [ ] Two consecutive disagreeing samples do not change it.
- [ ] The third consecutive disagreeing sample changes it.
- [ ] A disagreeing run broken by one agreeing sample starts over, so an alternating sequence never changes the Verdict.
- [ ] Recovery obeys the same rule as deterioration: three consecutive healthy samples to clear a `critical` Verdict.
- [ ] A Verdict jumping straight from healthy to critical is subject to the same count as a step through degraded.
- [ ] The daemon reaches a published Verdict promptly after startup rather than staying unjudged while the first run accumulates.
- [ ] The numeric thresholds that classify an individual sample are unchanged by this ticket.
- [ ] Hysteresis state is not written to the store, and a restart resets it.

## What to build

The daemon repairs, once, the two problems that earlier code left on disk: Entity and Relation rows whose Provenance is over the bound, and index shards that nothing can read any more.

Bounding writes fixes rows going forward, but a cold row is only rewritten when something mentions it again, so a store already over the line would stay there indefinitely. One startup pass brings the whole store under the bound instead. The dead shards are deleted in the same pass.

It runs as a single walk of the store, records that it completed so later boots skip the scan, and does not hold up readiness — a large one-time recovery must not look like a failed start. It reports what it did so the Operator can confirm the space actually came back.

The trim keeps the newest ids, exactly as the write-time bound does. Nothing recallable is touched by either job: this is Reclaim, not Eviction.

## Acceptance criteria

- [ ] On first run against a store with over-bound rows, every such row ends at or under the bound, keeping the newest ids.
- [ ] Rows already under the bound are left untouched, ids and order intact.
- [ ] Dead index shard data is removed from the store.
- [ ] Nothing recallable is removed: the same query returns the same Memories before and after the pass.
- [ ] A second run is a no-op that neither rescans the store nor logs noise.
- [ ] The pass does not delay readiness, and the daemon serves requests while it runs.
- [ ] The pass reports what it trimmed and what it reclaimed at a level the Operator will see.
- [ ] A failure partway through leaves the store consistent and does not prevent the daemon from starting.
- [ ] The pass is reachable as one entry point taking the open store, so it can be driven directly in tests.
